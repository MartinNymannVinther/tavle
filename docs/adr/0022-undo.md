# ADR 0022: Undo — every event carries its own reverse

Status: accepted · Date: 2026-09-14 (proposed and accepted the same day; the owner chose the full history over a last-action toast)

## Context

The owner wants to always be able to undo an action. The safety net was
prevention (confirm dialogs, deactivate-instead-of-delete, the close
conversation) and record (the append-only audit log, the event log) —
neither a way _back_. A last-action toast was sketched as v1; the owner
asked for the full solution instead: any past action, undone from where
its history is read.

## Decision

**The event log is the undo surface.** Every service that knows its
"before" writes the minimal reverse into its event (`payload.undo`,
carried by `recordEvent`): a move knows the column and index it left, a
placement knows the old parent, area and themes, a field edit knows the
old values, a creation knows that deletion is its reverse, an archive
knows restore, a sprint commit knows the old sprint, a close knows
reopen, the view change knows the old flags, a list entry knows its old
active state. The activity feeds — the card's and the item's — render
"Fortryd" on any event that carries a reverse and has not been undone.

**An undo is a new action, never an erasure.** `undoEvent` validates
the carried reverse (zod), refuses an already-undone event, runs the
reverse through the same ordinary services — workspace-checked,
rule-checked, event-logged — and writes `undo.applied` into the same
feeds; the undone line stands struck through, history intact. A reverse
that removes the thing itself (undoing a creation) leaves its note in
the board's feed alone, since there is no row left to hang it on.

**Refusal is honest.** A rule that has started to bind since — the
feature closed, the lane deactivated, children appeared under a
reopened item — refuses the reverse with the conflict word, instead of
pretending the past is a file that can be put back.

**Outside the reach, deliberately:** deleting a card, board or
workspace (the confirm dialog remains the guard; recreation from audit
images is a different machine and would bypass the services), closing
with a children plan (each decision logged its own reversible events),
sprint start/close bookkeeping, and the undo itself (one level; undoing
an undo is redoing, a later decision).

## Trade-offs accepted

- Carrying the reverse is a discipline on every new event-writing
  service, like the RLS test on every new table; the undo test file is
  where a new kind proves itself.
- The reverse snapshots the "before" at write time; if the same field
  changed twice, undoing the older event restores the older value over
  the newer — the feed shows both lines, and the person chose which to
  undo.
